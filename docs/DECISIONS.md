## ADR-005 · Самастойнасць Claude у распрацоўцы і ініцыятыва пераходаў
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: аўтар — пачатковец і не хоча ўзгадняць кожны тэхнічны крок; акрамя таго, доўгія чаты дорага каштуюць у токенах.

Пытаць аўтара абавязкова толькі пра грошы, сакрэты, дзеянні ад яго імя ў знешніх акаўнтах, незваротныя дзеянні з гісторыяй/данымі і сэнс прадукту (што ўмее бот). (2) Claude сам сочыць за памерам чата і, калі ён разросся, сам прапануе пераход з гатовым промптам — мэта эканомія токенаў.

## ADR-006 · Архітэктура: лакальнае прыкладанне + вэб-старонкі для OBS, TypeScript
- Дата: 2026-10-10 · Статус: заменена ADR-009 (аўтар не хоча асобнага працэсу)
- Кантэкст: патрэбны оверлей, які стрымер рухае ў кожнай сцэне, док-панэль з кіраваннем і просты ўсталёўка на чужы кампутар.
- Рашэнне: невялікае лакальнае прыкладанне (фонавы працэс на кампутары стрымера) з убудаваным вэб-серверам на `localhost`. Яно аддае дзве старонкі: оверлей (дадаецца ў OBS як *Browser Source* — звычайная крыніца, якую можна рухаць і маштабаваць у кожнай сцэне) і док (OBS → *Docks → Custom Browser Docks*). Мова — **TypeScript** і на серверы (Node.js), і ў старонках. Унутры — модулі: `music provider` (Spotify; пазней YouTube), `request source` (баллы канала Twitch; пазней чат-каманды), агульная чарга і стан, вэб-інтэрфейс. Распаўсюд — адзін выканальны файл (спосаб зборкі выбераем на Этапе 5).
- Прычыны / альтэрнатывы: (а) родны плагін OBS на C++ — складана, зборка пад кожную версію OBS і АС, рызыка падзення OBS; (б) скрыпт OBS на Python/Lua — патрабуе ўсталяванага Python, слабыя магчымасці; (в) толькі Browser Source без сервера — оверлей і док не могуць надзейна дзяліць стан і бяспечна захоўваць tokens. Лакальны сервер — стандартны падыход для такіх прылад. TypeScript — адна мова на ўсё, шмат бібліятэк для Spotify/Twitch.
- Наступствы: налады і tokens карыстальніка захоўваюцца ў файле налад прыкладання ў профілі карыстальніка, а не ў `.env` (`.env` — толькі для распрацоўкі). OBS WebSocket для MVP не патрэбны.

## ADR-007 · Уласная чарга заказаў, Spotify атрымлівае песні па адной
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: Spotify Web API умее толькі **дадаваць** трэк у чаргу і **чытаць** чаргу; выдаліць трэк з чаргі або змяніць парадак нельга (публічнага endpoint няма, гл. форум Spotify for Developers). Аўтару патрэбны «выдаліць» і «прайграць зараз» без змены астатняй чаргі.
- Рашэнне: прыкладанне трымае сваю чаргу заказаў. У Spotify перадаецца толькі наступная песня, незадоўга да канца бягучай (або адразу — пры «прайграць зараз»: дадаць у чаргу Spotify + «наступная»). Выдаленне — проста з нашай чаргі (у Spotify яна яшчэ не трапіла). Калі заказаў няма, паказваем наступныя трэкі з кантэксту Spotify (`GET /me/player/queue`). Стан Spotify чытаем апытаннем кожныя ~1–3 с (push-падзей у Web API няма).
- Прычыны / альтэрнатывы: (а) класці ўсе заказы адразу ў чаргу Spotify — нельга выдаліць і пераставіць; (б) асобны плэйліст-«чарга» — прыбірае кантэкст стрымера і патрабуе лішніх правоў.
- Наступствы: кіраваць трэкамі з кантэксту Spotify (не заказамі) будзе абмежавана — дакладна высветлім пры рэалізацыі. Ліміты запытаў Spotify у Development Mode трэба праверыць на практыцы.

## ADR-008 · Падключэнне Spotify і Twitch для любога стрымера
- Дата: 2026-10-10 · Статус: прынята (спосаб аўтарызацыі Twitch удакладнены ў ADR-009)
- Кантэкст: з лютага 2026 Spotify Development Mode: да 5 карыстальнікаў на Client ID, уладальнік прыкладання павінен мець Premium; Extended Quota — толькі для арганізацый з 250k+ MAU (крыніцы: Spotify February 2026 Migration Guide, Web API Changelog July 2026). Кіраванне прайграваннем праз API патрабуе Premium. Twitch: абнавіць статус узнагароды (выканана / вярнуць баллы) можа толькі тое прыкладанне (Client ID), якое стварыла ўзнагароду (Twitch API Reference, Update Redemption Status).
- Рашэнне: **Spotify** — кожны стрымер стварае свой бясплатны Spotify Developer App (крокавая інструкцыя ў наладах прыкладання), устаўляе свой Client ID; аўтарызацыя праз Authorization Code + PKCE (без Client Secret). **Twitch** — адно наша Application тыпу *Public*, аўтарызацыя праз Device Code Flow (стрымер націскае «Падключыць» і ўводзіць код на twitch.tv); прыкладанне само стварае ўзнагароду «Заказаць песню», каб умець вяртаць баллы пры памылцы.
- Прычыны / альтэрнатывы: адзін агульны Spotify Client ID на ўсіх — максімум 5 стрымераў, гэта не працуе для распаўсюду. Існуючую ўзнагароду аўтара, створаную ў панэлі Twitch, можна чытаць, але нельга аўтаматычна вярнуць па ёй баллы.
- Наступствы: патрабаванне для карыстальнікаў — Spotify Premium. Па звестках трэцяга боку (не пацверджана Spotify), з чэрвеня 2026 аўтарызацыя Spotify можа дзейнічаць 6 месяцаў — прыкладанне павінна ўмець папрасіць падключыцца нанова.

## ADR-009 · Усё жыве ў OBS: статычнае вэб-прыкладанне ў браўзеры OBS
- Дата: 2026-10-10 · Статус: прынята (канал да оверлея ўдакладнены ў ADR-013)
- Кантэкст: аўтар не хоча нічога запускаць асобна і не хоча лішніх працэсаў — прыкладанне павінна стартаваць разам з OBS і «жыць» у ім. Спатрэбіцца рэакцыя візуалізацыі на гук.
- Рашэнне: прыкладанне — **статычны набор вэб-старонак** (TypeScript, зборка Vite), які выконваецца ўбудаваным браўзерам OBS (CEF). Асобнага сервера і працэсу няма.
  - **Док** (*Docks → Custom Browser Docks*) — «мозг»: падключэнні, чарга, кіраванне Spotify, падзеі Twitch, налады. Spotify Web API і Twitch API (Helix, EventSub WebSocket) выклікаюцца проста з браўзера. Tokens захоўваюцца ў `localStorage` браўзера OBS на кампутары стрымера і нікуды не адпраўляюцца.
  - **Оверлей** (*Browser Source*) — толькі малюе. Стан атрымлівае ад дока праз **obs-websocket** (убудаваны ў OBS з 28 версіі): запыт `BroadcastCustomEvent` → падзея `CustomEvent`.
  - **Рэакцыя на гук**: падзея obs-websocket `InputVolumeMeters` (узровень гуку крыніц OBS кожныя ~50 мс). Стрымер выбірае крыніцу (лепш асобная *Application Audio Capture* для Spotify, каб не рэагаваць на голас). Гэта рэакцыя на гучнасць/рытм, не поўны спектр частот (для спектра патрэбны родны C++-плагін — гл. BACKLOG).
  - **Адкуль загружаюцца старонкі**: пры распрацоўцы — лакальны dev-сервер Vite на `http://127.0.0.1`; для карыстальнікаў — статычны https-хостынг (выбар на Этапе 5). Аўтарызацыя Spotify — PKCE з redirect на старонку `callback` таго ж прыкладання.
  - **Аўтарызацыя Twitch**: implicit grant (усё ў браўзеры, без сакрэту) або Device Code Flow — выбраць на Этапе 4 пасля праверкі CORS у браўзеры OBS.
- Прычыны / альтэрнатывы: (а) лакальнае прыкладанне-працэс (ADR-006) — аўтар адхіліў; (б) родны плагін OBS на C++ — складаная зборка, рызыка падзення OBS; пакідаем як магчымае пашырэнне (спектр гуку). Плюсы выбранага: нуль працэсаў, нічога не трэба ўсталёўваць (дастаткова дадаць два URL у OBS), старт разам з OBS.
- Наступствы / рызыкі (праверыць на Этапе 2): ці працуе док, калі ён закрыты/схаваны ў OBS; ці дазваляе док OAuth-перанакіраванне (запасны варыянт — перанакіраванне ўсёй старонкі дока).
  - **Вынікі праверкі (2026-10-10, OBS 32.2.2):** перанакіраванне ўсёй старонкі дока працуе, `localStorage` захоўваецца; закрыты крыжыкам док **працягвае працаваць** (таймеры не запавольваюцца, OBS нават не паведамляе старонцы, што яна схавана); але калі док закрыты **пры запуску OBS**, ён не загружаецца, пакуль яго не адкрыюць (па кодзе obs-browser: браўзер дока ствараецца ў `showEvent`). Док і Browser Source маюць **агульны** `localStorage` і `BroadcastChannel`. Гл. ADR-015. Патрэбна ўключыць obs-websocket (у аўтара ён зараз выключаны) — пароль obs-websocket стрымер уводзіць у наладах дока. Мова кода не змянілася — TypeScript (з ADR-006).

## ADR-011 · Паведамленні ў чат ад імя стрымера, суіснаванне з іншымі прыкладаннямі
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: асобнага бота не будзе — усё пішацца ад акаўнта стрымера. У аўтара ёсць іншае прыкладанне (галасаванні, распрацоўваецца асобна ў Codex), якое робіць тое ж. Патрэбна бяспека: ніякіх неафіцыйных метадаў, каб не было рызыкі бана.
- Рашэнне: толькі **афіцыйныя Twitch API**: EventSub WebSocket для падзей, Helix `Send Chat Message` для паведамленняў, токен стрымера з **мінімальнымі scopes**: `channel:read:redemptions`, `channel:manage:redemptions`, `user:write:chat` (канчаткова — на Этапе 4). **Асобнае Twitch Application** для гэтага праекта (свой Client ID): свае ліміты EventSub і токены, не перасякаецца з прыкладаннем галасаванняў. Ніякага IRC-скрапінгу, эмуляцыі браўзера ці чужых tokens.
- Прычыны: некалькі прыкладанняў з рознымі Client ID могуць адначасова працаваць з адным акаўнтам — гэта звычайная сітуацыя для Twitch (тыя ж OBS, Streamer.bot і г. д.). Агульнае — толькі ліміт паведамленняў у чат на акаўнт; наша прыкладанне піша коратка і толькі ў адказ на заказ.

## ADR-012 · Стэк каркаса: Preact, уласны кліент obs-websocket, Vitest
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: Этап 2 — каркас статычнага прыкладання (ADR-009). Патрэбны лёгкі UI-фрэймворк, кліент obs-websocket і тэсты.
- Рашэнне:
  - **Preact 10** (≈4 КБ) з JSX; без `@preact/preset-vite` (JSX пераўтварае сам Vite праз `oxc`). Стан — уласнае маленькае сховішча `core/store.ts`, незалежнае ад UI, каб ядро тэставалася без браўзера.
  - **Уласны кліент obs-websocket 5.x** (`src/obs/client.ts`, ≈200 радкоў): Hello/Identify, аўтэнтыфікацыя SHA-256 праз WebCrypto, запыты, падзеі, перападключэнне. Без знешніх залежнасцей.
  - **Vite 8**, **TypeScript 7**, **Vitest 5**; старонкі `index`, `dock`, `overlay`, `callback` (multi-page). Dev-сервер толькі на `127.0.0.1:5173`.
  - Структура: `core` (чарга, правілы, пратакол, налады, таймер), `obs` (кліент, канал, гук), `providers/spotify`, `sources/twitch` (пакуль тэставыя), `i18n`, `ui/dock`, `ui/overlay`, `ui/callback`, `ui/shared`.
- Прычыны / альтэрнатывы: (а) Svelte/Solid — таксама лёгкія, але патрабуюць свайго кампілятара; Preact — звычайны JSX, мінімум магіі. (б) `obs-websocket-js` — працуе, але цягне `crypto-js`, `ws`, `msgpack` і г. д.; пратакол просты, свой кліент меншы і цалкам пакрыты тэстамі. (в) Vanilla TS без фрэймворка — шмат ручной працы з DOM у доку.
- Наступствы: залежнасці прыкладання — толькі `preact`. Аўтэнтыфікацыя патрабуе secure context (WebCrypto) — `http://127.0.0.1` і https яго даюць.

## ADR-013 · Канал док → оверлей: obs-browser `emit_event` (асноўны), BroadcastCustomEvent (запасны)
- Дата: 2026-10-10 · Статус: прынята (праверана ў OBS 32.2.2: `emit_event` працуе, 0 памылак на 6000+ паведамленняў; `BroadcastChannel` і `localStorage` таксама агульныя)
- Кантэкст: ADR-009 прадугледжваў `BroadcastCustomEvent`. Тады оверлей сам павінен падключацца да obs-websocket і ведаць пароль. Па кодзе obs-browser у дока **асобнае сховішча** (свой `CefRequestContext` з `cache_path`), таму оверлей не прачытае пароль з `localStorage` дока.
- Рашэнне: док адпраўляе паведамленні запытам obs-websocket `CallVendorRequest` → vendor `obs-browser`, request `emit_event` (рэгіструецца ў `obs-browser-plugin.cpp`). OBS сам дастаўляе іх ва ўсе Browser Source як падзею `window` `spotify-bot` (`event.detail` — нашы даныя). **Оверлею не патрэбны ні пароль, ні падключэнне.** Калі `emit_event` недаступны, док аўтаматычна пераходзіць на `BroadcastCustomEvent`; тады оверлей падключаецца сам, а пароль перадаецца ў `#hash` адраса (`overlay.html#obs=…&pw=…`, hash не адпраўляецца па сетцы). Дадаткова заўсёды — `BroadcastChannel` (праверка ў звычайным браўзеры без OBS). Паведамленні маюць `sid` + `seq`, паўторы з розных каналаў адкідаюцца.
  - Паведамленні: `state` (бягучая + 3 наступныя), `level` (гук 0…1, ≈20 разоў/с), `ping` (кожныя 2 с; разам з поўным `state`, каб оверлей пасля перазагрузкі хутка атрымаў стан).
  - Абмежаванне `emit_event`: даныя праходзяць праз `obs_data`, які губляе `null` і масівы прымітываў. Пратакол гэта ўлічвае (толькі масівы аб'ектаў; адсутнае поле = `null`), ёсць тэст.
- Прычыны / альтэрнатывы: пароль obs-websocket дае поўнае кіраванне OBS — лепш, калі ён ёсць толькі ў доку. Альтэрнатывы: агульны `localStorage` (па кодзе OBS не агульны — правяраецца на практыцы), пароль у URL заўсёды (менш бяспечна).
- Наступствы: оверлей атрымлівае ўзровень гуку праз док, а не сам. Калі док не працуе (закрыты і спынены), оверлей застаецца з апошнім станам. **Удакладнена ў ADR-015:** адпраўляе не абавязкова док, а старонка-лідар (док або оверлей); канал той жа.

## ADR-014 · Стыль інтэрфейсу дока і тэкстаў
- Дата: 2026-10-10 · Статус: прынята (патрабаванні аўтара пасля першага прагляду ў OBS)
- Рашэнне:
  - **Без кропкі ў канцы** апошняга сказа ў любым блоку тэксту (загалоўкі, статусы, падказкі, паведамленні). Унутры шматсказавага тэксту кропкі застаюцца. Правяраецца тэстам `src/i18n/i18n.test.ts`.
  - **Падказкі — пад значком «?»** (паўпразрысты, у правым куце загалоўка блока); тэкст усплывае на плашцы пры навядзенні. Сталых тэкстаў-падказак пад палямі няма.
  - Тэкст падказкі — **паўнавартаснае тлумачэнне блока** для чалавека, незнаёмага з тэхналогіямі: што гэта, навошта, як карыстацца. Не «нататка з размовы з аўтарам» і не тэхнічныя заўвагі (этапы распрацоўкі, назвы пратаколаў, «спіс з’яўляецца пасля…»).
  - **Без фонавых плашак-картак** у блоках: усё ў адным акне, зоны аддзяляюцца адступамі.
  - Тэхнічныя звесткі (версія obs-websocket, канал да оверлея) — толькі на ўкладцы «Праверка», не ў наладах.
- Наступствы: кампанент `Section` / `InfoTip` (`src/ui/dock/Section.tsx`) для ўсіх блокаў дока; тэксты падказак — ключы `*.help` у `src/i18n/be.ts`.

## ADR-015 · «Мозг» прыкладання не павінен залежаць ад таго, ці адкрыты док
- Дата: 2026-10-10 · Статус: прынята, рэалізавана і праверана аўтарам у OBS 32.2.2 (Web Locks ёсць і агульныя для дока і Browser Source)
- Кантэкст: праверка ў OBS (ADR-009) паказала, што док, закрыты пры запуску OBS, не загружаецца, пакуль стрымер яго не адкрые. Значыць, калі «мозг» (чарга, Spotify, заказы Twitch) жыве толькі ў доку, бот не працуе, пакуль док схаваны. Browser Source (оверлей) загружаецца разам са сцэнамі. Док і оверлей маюць агульны `localStorage` і `BroadcastChannel`.
- Прапанова: «мозг» можа працаваць у **любой** старонцы прыкладання — у доку або ў оверлеі. Адна з іх становіцца «лідарам» праз Web Locks API (`navigator.locks`, агульны для старонак з агульным сховішчам), астатнія — толькі паказваюць стан і перадаюць каманды лідару праз `BroadcastChannel`. Калі лідар знікае (док зачынены, оверлей выдалены), лідарам становіцца іншая старонка; стан захоўваецца ў `localStorage`. Уваход у Spotify/Twitch застаецца ў доку (патрэбны клікі стрымера), tokens — у агульным `localStorage`.
- Прычыны / альтэрнатывы: (а) прасіць стрымера трымаць док адкрытым — ненадзейна, лёгка забыць; (б) асобная схаваная Browser Source толькі для «мозга» — лішняя крыніца ў наладзе; (в) «мозг» толькі ў оверлеі — некалькі копій оверлея ў розных сцэнах пачнуць дубляваць работу, таму патрэбны лідар.
- Наступствы: канал `emit_event` (ADR-013) застаецца для выпадку, калі `BroadcastChannel` недаступны; трэба праверыць `navigator.locks` у браўзеры OBS.
- **Рэалізацыя (Этап 2.1, `src/brain/`):**
  - `leader.ts` — Web Lock `spotify-bot:leader`; лідар трымае замок, пакуль старонка жывая. Без `navigator.locks` лідарам можа быць толькі док (як было да ADR-015) — каб не запусціць некалькі мазгоў.
  - `brain.ts` — логіка з былога `ui/dock/controller.ts`: чарга, заказы, obs-websocket (падключае толькі лідар), адпраўка стану ў оверлей.
  - `node.ts` — старонка-ўдзельнік: лідар запускае мозг і рассылае стан праз `BroadcastChannel` `spotify-bot:brain` (пры змене, не часцей за 50 мс, і кожную секунду); астатнія паказваюць стан і шлюць каманды. UI не ведае, дзе мозг. Лідар, які заўважыў іншага лідара, лічыць «канфлікты» (паказваюцца ў «Праверцы» і debug-оверлеі).
  - `persist.ts` — стан плэера і чаргі ў `localStorage` (`spotify-bot:player:v1`) раз у секунду і пры спыненні лідара (да вызвалення замка). Новы лідар чытае яго і прасоўвае песню на час, які прайшоў. Налады — як і раней у `localStorage`; пра змену старонкі паведамляюць праз шыну і падзею `storage`.
  - Ключы запісаў чаргі ўтрымліваюць ідэнтыфікатар старонкі — не паўтараюцца пры змене лідара.
  - Оверлей з `?demo=1` у выбары не ўдзельнічае.
