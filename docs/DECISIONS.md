## ADR-005 · Самастойнасць Claude у распрацоўцы і ініцыятыва пераходаў
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: аўтар — пачатковец і не хоча ўзгадняць кожны тэхнічны крок; акрамя таго, доўгія чаты дорага каштуюць у токенах.
- Рашэнне: (1) у распрацоўцы Claude дзейнічае сам і працуе столькі, колькі трэба: выбірае рашэнні, піша код, ставіць залежнасці, правярае, робіць commit, push і зліццё сваіх галін у `main`. Пытаць аўтара абавязкова толькі пра грошы, сакрэты, дзеянні ад яго імя ў знешніх акаўнтах, незваротныя дзеянні з гісторыяй/данымі і сэнс прадукту (што ўмее бот). (2) Claude сам сочыць за памерам чата і, калі ён разросся, сам прапануе пераход з гатовым промптам — мэта эканомія токенаў.
- Прычыны / альтэрнатывы: альтэрнатыва «пытаць пра кожны крок» запавольвае працу і перакладае на пачаткоўца тэхнічныя рашэнні.

## ADR-006 · Архітэктура: лакальнае прыкладанне + вэб-старонкі для OBS, TypeScript
- Дата: 2026-10-10 · Статус: заменена ADR-009 (аўтар не хоча асобнага працэсу)
- Кантэкст: патрэбны оверлей, які стрымер рухае ў кожнай сцэне, док-панэль з кіраваннем і просты ўсталёўка на чужы кампутар.
- Рашэнне: невялікае лакальнае прыкладанне (фонавы працэс на кампутары стрымера) з убудаваным вэб-серверам на `localhost`. Яно аддае дзве старонкі: оверлей (дадаецца ў OBS як *Browser Source* — звычайная крыніца, якую можна рухаць і маштабаваць у кожнай сцэне) і док (OBS → *Docks → Custom Browser Docks*). Мова — **TypeScript** і на серверы (Node.js), і ў старонках. Унутры — модулі: `music provider` (Spotify; пазней YouTube), `request source` (баллы канала Twitch; пазней чат-каманды), агульная чарга і стан, вэб-інтэрфейс. Распаўсюд — адзін выканальны файл (спосаб зборкі выбераем на Этапе 5).
- Прычыны / альтэрнатывы: (а) родны плагін OBS на C++ — складана, зборка пад кожную версію OBS і АС, рызыка падзення OBS; (б) скрыпт OBS на Python/Lua — патрабуе ўсталяванага Python, слабыя магчымасці; (в) толькі Browser Source без сервера — оверлей і док не могуць надзейна дзяліць стан і бяспечна захоўваць tokens. Лакальны сервер — стандартны падыход для такіх прылад. TypeScript — адна мова на ўсё, шмат бібліятэк для Spotify/Twitch.
- Наступствы: налады і tokens карыстальніка захоўваюцца ў файле налад прыкладання ў профілі карыстальніка, а не ў `.env` (`.env` — толькі для распрацоўкі). OBS WebSocket для MVP не патрэбны.

## ADR-007 · Уласная чарга заказаў, Spotify атрымлівае песні па адной
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: Spotify Web API умее толькі **дадаваць** трэк у чаргу і **чытаць** чаргу; выдаліць трэк з чаргі або змяніць парадак нельга (публічнага endpoint няма, гл. форум Spotify for Developers). Аўтару патрэбны «выдаліць» і «прайграць зараз» без змены астатняй чаргі.
- Рашэнне: прыкладанне трымае сваю чаргу заказаў. У Spotify перадаецца толькі наступная песня, незадоўга да канца бягучай (або адразу — пры «прайграць зараз»: дадаць у чаргу Spotify + «наступная»). Выдаленне — проста з нашай чаргі (у Spotify яна яшчэ не трапіла). Калі заказаў няма, паказваем наступныя трэкі з кантэксту Spotify (`GET /me/player/queue`). Стан Spotify чытаем апытаннем кожныя ~1–3 с (push-падзей у Web API няма).
- Прычыны / альтэрнатывы: (а) класці ўсе заказы адразу ў чаргу Spotify — нельга выдаліць і пераставіць; (б) асобны плэйліст-«чарга» — прыбірае кантэкст стрымера і патрабуе лішніх правоў.
- Наступствы: кіраваць трэкамі з кантэксту Spotify (не заказамі) будзе абмежавана — дакладна высветлім пры рэалізацыі. Ліміты запытаў Spotify у Development Mode трэба праверыць на практыцы.
- **Удакладнена ў ADR-016:** апытанне не кожныя 1–3 с, а ашчаднае (6 с і ў момант канца песні) — з-за квоты Development Mode.
- **Рэалізацыя — ADR-017** (Этап 3б): пошук, адпраўка за 15 с да канца песні, зверка з чаргой Spotify.

## ADR-008 · Падключэнне Spotify і Twitch для любога стрымера
- Дата: 2026-10-10 · Статус: прынята (спосаб аўтарызацыі Twitch удакладнены ў ADR-009)
- Кантэкст: з лютага 2026 Spotify Development Mode: да 5 карыстальнікаў на Client ID, уладальнік прыкладання павінен мець Premium; Extended Quota — толькі для арганізацый з 250k+ MAU (крыніцы: Spotify February 2026 Migration Guide, Web API Changelog July 2026). Кіраванне прайграваннем праз API патрабуе Premium. Twitch: абнавіць статус узнагароды (выканана / вярнуць баллы) можа толькі тое прыкладанне (Client ID), якое стварыла ўзнагароду (Twitch API Reference, Update Redemption Status).
- Рашэнне: **Spotify** — кожны стрымер стварае свой бясплатны Spotify Developer App (крокавая інструкцыя ў наладах прыкладання), устаўляе свой Client ID; аўтарызацыя праз Authorization Code + PKCE (без Client Secret). **Twitch** — адно наша Application тыпу *Public*, аўтарызацыя праз Device Code Flow (стрымер націскае «Падключыць» і ўводзіць код на twitch.tv); прыкладанне само стварае ўзнагароду «Заказаць песню», каб умець вяртаць баллы пры памылцы.
- Прычыны / альтэрнатывы: адзін агульны Spotify Client ID на ўсіх — максімум 5 стрымераў, гэта не працуе для распаўсюду. Існуючую ўзнагароду аўтара, створаную ў панэлі Twitch, можна чытаць, але нельга аўтаматычна вярнуць па ёй баллы.
- Наступствы: патрабаванне для карыстальнікаў — Spotify Premium. Па звестках трэцяга боку (не пацверджана Spotify), з чэрвеня 2026 аўтарызацыя Spotify можа дзейнічаць 6 месяцаў — прыкладанне павінна ўмець папрасіць падключыцца нанова.

## ADR-009 · Усё жыве ў OBS: статычнае вэб-прыкладанне ў браўзеры OBS
- Дата: 2026-10-10 · Статус: прынята (канал да оверлея ўдакладнены ў ADR-013)
- Кантэкст: аўтар не хоча нічога запускаць асобна і не хоча лішніх працэсаў — прыкладанне павінна стартаваць разам з OBS і «жыць» у ім. Спатрэбіцца рэакцыя візуалізацыі на гук.
- Рашэнне: прыкладанне — **статычны набор вэб-старонак** (TypeScript, зборка Vite), які выконваецца ўбудаваным браўзерам OBS (CEF). Асобнага сервера і працэсу няма.
  - **Док** (*Docks → Custom Browser Docks*) — «мозг»: падключэнні, чарга, кіраванне Spotify, падзеі Twitch, налады. Spotify Web API і Twitch API (Helix, EventSub WebSocket) выклікаюцца проста з браўзера. Tokens захоўваюцца ў `localStorage` браўзера OBS на кампутары стрымера і нікуды не адпраўляюцца.
  - **Оверлей** (*Browser Source*) — толькі малюе. Стан атрымлівае ад дока праз **obs-websocket** (убудаваны ў OBS з 28 версіі): запыт `BroadcastCustomEvent` → падзея `CustomEvent`.
  - **Рэакцыя на гук**: падзея obs-websocket `InputVolumeMeters` (узровень гуку крыніц OBS кожныя ~50 мс). Стрымер выбірае крыніцу (лепш асобная *Application Audio Capture* для Spotify, каб не рэагаваць на голас). Гэта рэакцыя на гучнасць/рытм, не поўны спектр частот (для спектра патрэбны родны C++-плагін — гл. BACKLOG).
  - **Адкуль загружаюцца старонкі**: пры распрацоўцы — лакальны dev-сервер Vite на `http://127.0.0.1`; для карыстальнікаў — статычны https-хостынг (выбар на Этапе 5). Аўтарызацыя Spotify — PKCE з redirect на старонку `callback` таго ж прыкладання.
  - **Аўтарызацыя Twitch**: implicit grant (усё ў браўзеры, без сакрэту) або Device Code Flow — выбраць на Этапе 4 пасля праверкі CORS у браўзеры OBS. **Выбрана Device Code Flow, CORS правераны — ADR-018.**
- Прычыны / альтэрнатывы: (а) лакальнае прыкладанне-працэс (ADR-006) — аўтар адхіліў; (б) родны плагін OBS на C++ — складаная зборка, рызыка падзення OBS; пакідаем як магчымае пашырэнне (спектр гуку). Плюсы выбранага: нуль працэсаў, нічога не трэба ўсталёўваць (дастаткова дадаць два URL у OBS), старт разам з OBS.
- Наступствы / рызыкі (праверыць на Этапе 2): ці працуе док, калі ён закрыты/схаваны ў OBS; ці дазваляе док OAuth-перанакіраванне (запасны варыянт — перанакіраванне ўсёй старонкі дока).
  - **Вынікі праверкі (2026-10-10, OBS 32.2.2):** перанакіраванне ўсёй старонкі дока працуе, `localStorage` захоўваецца; закрыты крыжыкам док **працягвае працаваць** (таймеры не запавольваюцца, OBS нават не паведамляе старонцы, што яна схавана); але калі док закрыты **пры запуску OBS**, ён не загружаецца, пакуль яго не адкрыюць (па кодзе obs-browser: браўзер дока ствараецца ў `showEvent`). Док і Browser Source маюць **агульны** `localStorage` і `BroadcastChannel`. Гл. ADR-015. Патрэбна ўключыць obs-websocket (у аўтара ён зараз выключаны) — пароль obs-websocket стрымер уводзіць у наладах дока. Мова кода не змянілася — TypeScript (з ADR-006).

## ADR-010 · Мовы прыкладання: беларуская
- Дата: 2026-10-10 · Статус: прынята
- Рашэнне: тэксты для гледачоў (оверлей, паведамленні ў чаце) і інтэрфейс дока/налад — **па-беларуску**. Тэксты трымаем у адным месцы (файл перакладаў), каб пазней лёгка дадаць іншыя мовы. Платформа — **Windows** (OBS 32+).
- **Дапаўненне (2026-10-11, вычытка па заўвагах аўтара):** сумнеўныя словы правяраем па слоўніках (skarnik.by — руска-беларускі НАН; verbum.by — ТСБМ, Тлумачальны слоўнік Капылова 2022, граматычная база Інстытута мовазнаўства), а не па машынным перакладзе. Прынятыя тэрміны: **замова / замовіць** (не «заказ»), **балы, балаў** (бал — з адным «л»), **кошт**, **чарга**, **оверлэй** (скланяецца як «музей»: оверлэя, оверлэю, у оверлэі), **перададзена** (не «адпраўлена»), **уключыць зараз** (не «прайграць» — асноўнае значэнне «прайграць» — «проиграть»), **капіяваць / скапіюйце** (варыянт «капіраваць» таксама літаратурны, у праграме — адзін), укладка **«Стан»**. Колькасць у тэкстах — без залежных ад ліку канчаткаў («кошт — {N}», «максімум песень ({N})»). Тэст `i18n.test.ts` не дае вярнуць вядомыя памылкі.

## ADR-011 · Паведамленні ў чат ад імя стрымера, суіснаванне з іншымі прыкладаннямі
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: асобнага бота не будзе — усё пішацца ад акаўнта стрымера. У аўтара ёсць іншае прыкладанне (галасаванні, распрацоўваецца асобна ў Codex), якое робіць тое ж. Патрэбна бяспека: ніякіх неафіцыйных метадаў, каб не было рызыкі бана.
- Рашэнне: толькі **афіцыйныя Twitch API**: EventSub WebSocket для падзей, Helix `Send Chat Message` для паведамленняў, токен стрымера з **мінімальнымі scopes**: `channel:read:redemptions`, `channel:manage:redemptions`, `user:write:chat` (канчаткова — на Этапе 4; **ADR-018:** толькі `channel:manage:redemptions` і `user:write:chat`). **Асобнае Twitch Application** для гэтага праекта (свой Client ID): свае ліміты EventSub і токены, не перасякаецца з прыкладаннем галасаванняў. Ніякага IRC-скрапінгу, эмуляцыі браўзера ці чужых tokens.
- Прычыны: некалькі прыкладанняў з рознымі Client ID могуць адначасова працаваць з адным акаўнтам — гэта звычайная сітуацыя для Twitch (тыя ж OBS, Streamer.bot і г. д.). Агульнае — толькі ліміт паведамленняў у чат на акаўнт; наша прыкладанне піша коратка і толькі ў адказ на заказ.

## ADR-012 · Стэк каркаса: Preact, уласны кліент obs-websocket, Vitest
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: Этап 2 — каркас статычнага прыкладання (ADR-009). Патрэбны лёгкі UI-фрэймворк, кліент obs-websocket і тэсты.
- Рашэнне:
  - **Preact 10** (≈4 КБ) з JSX; без `@preact/preset-vite` (JSX пераўтварае сам Vite праз `oxc`). Стан — уласнае маленькае сховішча `core/store.ts`, незалежнае ад UI, каб ядро тэставалася без браўзера.
  - **Уласны кліент obs-websocket 5.x** (`src/obs/client.ts`, ≈200 радкоў): Hello/Identify, аўтэнтыфікацыя SHA-256 праз WebCrypto, запыты, падзеі, перападключэнне. Без знешніх залежнасцей.
  - **Vite 8**, **TypeScript 7**, **Vitest 5**; старонкі `index`, `dock`, `overlay`, `callback` (multi-page). Dev-сервер толькі на `127.0.0.1:5173`.
  - Структура: `core` (чарга, правілы, пратакол, налады, таймер), `obs` (кліент, канал, гук), `providers/spotify`, `sources/twitch` (пакуль тэставыя), `i18n`, `ui/dock`, `ui/overlay`, `ui/callback`, `ui/shared`.
- Прычыны / альтэрнатывы: (а) Svelte/Solid — таксама лёгкія, але патрабуюць свайго кампілятара; Preact — звычайны JSX, мінімум магіі. (б) `obs-websocket-js` — працуе, але цягне `crypto-js`, `ws`, `msgpack` і г. д.; пратакол просты, свой кліент меншы і цалкам пакрыты тэстамі. (в) Vanilla TS без фрэймворка — шмат ручной працы з DOM у доку.
- Наступствы: залежнасці прыкладання — толькі `preact`. Аўтэнтыфікацыя патрабуе secure context (WebCrypto) — `http://127.0.0.1` і https яго даюць.

## ADR-013 · Канал док → оверлей: obs-browser `emit_event` (асноўны), BroadcastCustomEvent (запасны)
- Дата: 2026-10-10 · Статус: прынята (праверана ў OBS 32.2.2: `emit_event` працуе, 0 памылак на 6000+ паведамленняў; `BroadcastChannel` і `localStorage` таксама агульныя)
- Кантэкст: ADR-009 прадугледжваў `BroadcastCustomEvent`. Тады оверлей сам павінен падключацца да obs-websocket і ведаць пароль. Па кодзе obs-browser у дока **асобнае сховішча** (свой `CefRequestContext` з `cache_path`), таму оверлей не прачытае пароль з `localStorage` дока.
- Рашэнне: док адпраўляе паведамленні запытам obs-websocket `CallVendorRequest` → vendor `obs-browser`, request `emit_event` (рэгіструецца ў `obs-browser-plugin.cpp`). OBS сам дастаўляе іх ва ўсе Browser Source як падзею `window` `spotify-bot` (`event.detail` — нашы даныя). **Оверлею не патрэбны ні пароль, ні падключэнне.** Калі `emit_event` недаступны, док аўтаматычна пераходзіць на `BroadcastCustomEvent`; тады оверлей падключаецца сам, а пароль перадаецца ў `#hash` адраса (`overlay.html#obs=…&pw=…`, hash не адпраўляецца па сетцы). Дадаткова заўсёды — `BroadcastChannel` (праверка ў звычайным браўзеры без OBS). Паведамленні маюць `sid` + `seq`, паўторы з розных каналаў адкідаюцца.
  - Паведамленні: `state` (бягучая + 3 наступныя), `level` (гук 0…1, ≈20 разоў/с), `ping` (кожныя 2 с; разам з поўным `state`, каб оверлей пасля перазагрузкі хутка атрымаў стан).
  - Абмежаванне `emit_event`: даныя праходзяць праз `obs_data`, які губляе `null` і масівы прымітываў. Пратакол гэта ўлічвае (толькі масівы аб'ектаў; адсутнае поле = `null`), ёсць тэст.
- Прычыны / альтэрнатывы: пароль obs-websocket дае поўнае кіраванне OBS — лепш, калі ён ёсць толькі ў доку. Альтэрнатывы: агульны `localStorage` (па кодзе OBS не агульны — правяраецца на практыцы), пароль у URL заўсёды (менш бяспечна).
- Наступствы: оверлей атрымлівае ўзровень гуку праз док, а не сам. Калі док не працуе (закрыты і спынены), оверлей застаецца з апошнім станам. **Удакладнена ў ADR-015:** адпраўляе не абавязкова док, а старонка-лідар (док або оверлей); канал той жа.

- Рашэнне:
  - **Без кропкі ў канцы** апошняга сказа ў любым блоку тэксту (загалоўкі, статусы, падказкі, паведамленні). Унутры шматсказавага тэксту кропкі застаюцца. Правяраецца тэстам `src/i18n/i18n.test.ts`.

Мэта — чалавек без вопыту наладжвае ўсё толькі па падказках.

## ADR-015 · «Мозг» прыкладання не павінен залежаць ад таго, ці адкрыты док
- Дата: 2026-10-10 · Статус: прынята, рэалізавана і праверана аўтарам у OBS 32.2.2 (Web Locks ёсць і агульныя для дока і Browser Source)
- Кантэкст: праверка ў OBS (ADR-009) паказала, што док, закрыты пры запуску OBS, не загружаецца, пакуль стрымер яго не адкрые. Значыць, калі «мозг» (чарга, Spotify, заказы Twitch) жыве толькі ў доку, бот не працуе, пакуль док схаваны. Browser Source (оверлей) загружаецца разам са сцэнамі. Док і оверлей маюць агульны `localStorage` і `BroadcastChannel`.
- Прапанова: «мозг» можа працаваць у **любой** старонцы прыкладання — у доку або ў оверлеі. Адна з іх становіцца «лідарам» праз Web Locks API (`navigator.locks`, агульны для старонак з агульным сховішчам), астатнія — толькі паказваюць стан і перадаюць каманды лідару праз `BroadcastChannel`. Калі лідар знікае (док зачынены, оверлей выдалены), лідарам становіцца іншая старонка; стан захоўваецца ў `localStorage`. Уваход у Spotify/Twitch застаецца ў доку (патрэбны клікі стрымера), tokens — у агульным `localStorage`.
- Прычыны / альтэрнатывы: (а) прасіць стрымера трымаць док адкрытым — ненадзейна, лёгка забыць; (б) асобная схаваная Browser Source толькі для «мозга» — лішняя крыніца ў наладзе; (в) «мозг» толькі ў оверлеі — некалькі копій оверлея ў розных сцэнах пачнуць дубляваць работу, таму патрэбны лідар.
- Наступствы: канал `emit_event` (ADR-013) застаецца для выпадку, калі `BroadcastChannel` недаступны; трэба праверыць `navigator.locks` у браўзеры OBS.
- **Рэалізацыя (Этап 2.1, `src/brain/`):**
  - `leader.ts` — Web Lock `spotify-bot:leader`; лідар трымае замок, пакуль старонка жывая. Без `navigator.locks` лідарам можа быць толькі док (як было да ADR-015) — каб не запусціць некалькі мазгоў.
  - `brain.ts` — логіка з былога `ui/dock/controller.ts`: чарга, заказы, obs-websocket (падключае толькі лідар), адпраўка стану ў оверлей.
  - `node.ts` — старонка-ўдзельнік: лідар запускае мозг і рассылае стан праз `BroadcastChannel` `spotify-bot:brain` (пры змене, не часцей за 50 мс, і кожную секунду); астатнія паказваюць стан і шлюць каманды. UI не ведае, дзе мозг. Лідар, які заўважыў іншага лідара, лічыць «канфлікты» (паказваюцца ў «Праверцы» і debug-оверлеі).
  - `persist.ts` — стан плэера і чаргі ў `localStorage` (`spotify-bot:player:v1`) раз у секунду і пры спыненні лідара (да вызвалення замка). Новы лідар чытае яго і прасоўвае песню на час, які прайшоў. Налады — як і раней у `localStorage`; пра змену старонкі паведамляюць праз шыну і падзею `storage`.
  - Ключы запісаў чаргі ўтрымліваюць ідэнтыфікатар старонкі — не паўтараюцца пры змене лідара.
  - Оверлей з `?demo=1` у выбары не ўдзельнічае.

## ADR-016 · Падключэнне Spotify: PKCE, токены ў localStorage, ашчадны апытанне
- Дата: 2026-10-10 · Статус: прынята (Этап 3а)
- Кантэкст: правілы Spotify Web API на кастрычнік 2026 (крыніцы: February 2026 Migration Guide і Changelog, блог «Introducing refresh token expiration» 2026-06-18, блог «Web API quota updates for Development Mode» 2026-07-23, старонкі Redirect URIs, Quota modes, Authorization Code with PKCE):
  - **Development Mode:** уладальнік прыкладання — з Premium; да 5 карыстальнікаў на прыкладанне (іх дадаюць у *User Management*, іначай API адказвае 403); да 25 Client ID на акаўнт распрацоўшчыка; **квота агульная на ўвесь акаўнт распрацоўшчыка** і не апублікавана. Пры яе вычарпанні — `429` з `"reason": "QUOTA_EXCEEDED"` і `Retry-After` на некалькі гадзін. Па справаздачах распрацоўшчыкаў (не Spotify): апытанне плэера кожныя 3 с кругласутачна вычэрпвае квоту прыкладна за суткі.
  - **Redirect URI:** толькі https, або http на IP-адрасе loopback (`http://127.0.0.1:ПОРТ/…`); `localhost` забаронены; адрас павінен супадаць дакладна.
  - **Токены:** Authorization Code + PKCE (без Client Secret), запыт токена з браўзера (`POST https://accounts.spotify.com/api/token`, form-urlencoded). **Refresh token дзейнічае 6 месяцаў** ад уваходу (абнаўленне не падаўжае); пасля — `400 invalid_grant`, трэба ўвайсці нанова, не паўтараць запыт. Пры абнаўленні Spotify можа не вярнуць новы refresh token — тады пакідаем стары.
  - **«Любімыя трэкі»:** `PUT /me/tracks` і `GET /me/tracks/contains` **выдалены** (люты 2026). Замена: `PUT /v1/me/library?uris=spotify:track:…` (scope `user-library-modify`) і `GET /v1/me/library/contains?uris=…` (scope `user-library-read`, адказ — масіў `true/false`), да 40 URI.
  - **Плэер** не змяніўся: `GET /me/player`, `GET /me/player/queue`, `PUT /me/player/play`, `PUT /me/player/pause`, `POST /me/player/next`, `POST /me/player/previous`, `POST /me/player/queue` (спатрэбіцца на Этапе 3б). Push-падзей у Web API няма. У трэка выдалены `popularity`, `available_markets`, `linked_from` — мы іх не выкарыстоўваем; `explicit`, `duration_ms`, `uri` засталіся.
- Рашэнне:
  - **Client ID** стрымер уводзіць у наладах дока (`settings.spotify.clientId`). Док паказвае Redirect URI, які трэба ўставіць у Spotify Dashboard (пры распрацоўцы — `http://127.0.0.1:5173/callback.html`).
  - **Scopes:** `user-read-playback-state`, `user-read-currently-playing`, `user-modify-playback-state`, `user-library-read`, `user-library-modify`. Іх хопіць і для Этапа 3б (дадаць у чаргу Spotify) і пошуку трэкаў (пошуку scope не патрэбны).
  - **Уваход:** док запісвае ў `localStorage` `verifier` і `state`, пераходзіць усёй старонкай на `accounts.spotify.com/authorize` → Spotify вяртае на `callback.html` → старонка вяртання сама абменьвае код на токены, захоўвае іх і вяртае док на ўкладку «Налады». Popup не выкарыстоўваем (з дока ён адкрываецца ў сістэмным браўзеры, ADR-009).
  - **Токены** — у `localStorage` (`spotify-bot:spotify:tokens:v1`) разам з Client ID, якім выдадзены, і часам уваходу. З Spotify размаўляе **толькі лідар** (ADR-015): ён абнаўляе access token (за 60 с да канца), на `401` — адзін раз абнаўляе і паўтарае. Токены лідар кожны раз чытае з `localStorage`, таму новы ўваход са старонкі вяртання ён бачыць адразу. Абноўленыя токены не запісваюцца, калі за гэты час іх замяніў новы ўваход. `invalid_grant` → токены выдаляюцца, док просіць увайсці зноў.
  - **Апытанне (замест «кожныя 1–3 с» з ADR-007):** `GET /me/player` — кожныя 6 с, калі грае; у момант чаканага канца песні (+0,5 с); праз 0,7 с пасля кнопкі; 15 с — на паўзе; 30 с — калі Spotify нідзе не адкрыты. `GET /me/player/queue` — пры змене песні і раз у 2 хв; `GET /me/library/contains` — пры змене песні. Паміж апытаннямі час песні лічыцца лакальна. Разлік: каля 600 запытаў у гадзіну падчас музыкі — значна менш, чым 1200/гадз пры 3 с, ад якіх, па справаздачах, квота сканчаецца. Колькасць запытаў за дзень паказваецца на ўкладцы «Праверка» — па ёй удакладнім інтэрвалы.
  - **429:** чакаем `Retry-After` (калі яго няма — 1 гадзіна для `QUOTA_EXCEEDED`, 5 с для звычайнага ліміту), пакуль што — апошні вядомы стан і паведамленне ў доку з часам, калі працягнем.
  - **Без Spotify** бот нічога не грае і **не паказвае выдуманых песень** (каб на стрыме не з’явіліся тэставыя даныя, напрыклад пасля заканчэння 6 месяцаў уваходу). Тэставы плэйліст застаецца толькі для тэстаў і `overlay.html?demo=1`.
  - Тэставыя заказы (кнопка «+ Тэставы заказ») пры падключаным Spotify схаваны: выдуманыя трэкі нельга адправіць у Spotify. Сапраўдныя заказы ў Spotify — Этап 3б.
- Прычыны / альтэрнатывы: (а) Web Playback SDK — ператварыў бы OBS у плэер, стрымер слухае Spotify у сваім дадатку — не патрэбны; (б) implicit grant — Spotify яго больш не рэкамендуе, без refresh token; (в) апытанне кожныя 1–3 с — рызыка блакіроўкі на гадзіны.
- Наступствы: ручное пераключэнне ў Spotify відаць у доку і оверлеі са спазненнем да 6 с (натуральны канец песні — амаль адразу). Кожныя 6 месяцаў стрымер падключае Spotify нанова. Стрымер дадае сябе ў *User Management* свайго прыкладання, калі Spotify адказвае 403.
- **Дапаўненне (2026-10-10, пасля праверкі аўтарам, commit `c405d57`):**
  - **Кнопкі дока:** «Наступная» паказвае першую песню з чаргі адразу, «Папярэдняя» — песню з гісторыі (або тую ж нанова пасля 3 с), паўза — адразу. Потым бот правярае Spotify праз 0,3 с і кожныя 0,4 с, пакуль Spotify не пацвердзіць (да 4 с). «Старыя» адказы Spotify за гэты час не паказваюцца — песня не мільгае назад. У браўзеры: новая песня ў доку праз ~10 мс пасля кліку (было 2–6 с).
  - **Змены ў самім Spotify:** лідар раз у секунду чытае праз obs-websocket спіс акон з налад крыніцы OBS «Захват звука приложения» / «Захват окна» / «Захват игры» (`GetInputList`, `GetInputPropertiesListPropertyItems`, уласцівасць `window`) і шукае акно `Spotify.exe`. Яго загаловак — «Выканаўца - Назва» або «Spotify Premium» на паўзе. Змена загалоўка (іншая песня, паўза, Spotify адкрыты/закрыты) — сігнал апытаць Spotify праз 0,25 с. Да Spotify гэта не дадае запытаў, акрамя таго аднаго апытання. Без такой крыніцы ў OBS, без падключэння да OBS або калі Spotify згорнуты (OBS можа не паказваць згорнутыя вокны — не праверана) — працуе звычайнае апытанне. `src/obs/spotify-window.ts`.
  - **Spotify нідзе не адкрыты:** апытанне раз у 15 с (было 30 с).
  - **Гучнасць:** `PUT /me/player/volume?volume_percent=…` (scope `user-modify-playback-state` ужо ёсць); гучнасць і `supports_volume` — з `device` у `GET /me/player`. Пакуль цягнуць паўзунок — не часцей за раз у 300 мс, апошняе значэнне заўсёды адпраўляецца; 2,5 с пасля змены гучнасць з апытання не перазапісвае паўзунок.
- **Дапаўненне 2 (2026-10-10, Этап 3б, commit `65ae59e`):** калі бот бачыць акно Spotify праз OBS («Праверка» → Spotify — зялёны радок), пра змену песні, паўзу і адкрыццё Spotify паведамляе загаловак акна, таму апытанне радзей: грае — 20 с (было 6 с; **пасля праверкі аўтарам — 10 с**, каб перамотка была відаць хутчэй), паўза і «нідзе не адкрыты» — 30 с (было 15 с); **пакуль чакае неадпраўлены заказ — 5 с** (ADR-017); у канцы песні — як і раней. Калі бот перастаў бачыць акно — адразу вяртаецца да частага апытання. Разлік: раней падчас музыкі ~680 запытаў/гадз, на паўзе ~240/гадз → стрым 4 гадз + 4 гадз OBS без музыкі ≈ 3,7 тыс. за дзень (каля 13 % ад ~29 тыс./дзень, пры якіх, па справаздачах, квота сканчаецца); цяпер з акном — ~230 і ~120/гадз ≈ 1,4 тыс. за дзень. Заказы дадаюць 1–3 запыты на заказ (пошук, адпраўка ў чаргу).

## ADR-017 · Заказы гледачоў → Spotify: пошук, адпраўка незадоўга да канца песні, зверка з чаргой
- Дата: 2026-10-10 · Статус: прынята (Этап 3б; праверана тэстамі і ў браўзеры з падробкай Spotify, у OBS — чакае праверкі аўтарам)
- Кантэкст: ADR-007 — наша чарга заказаў галоўная, у Spotify — па адной песні. Дакументацыя Spotify на кастрычнік 2026 (February 2026 Migration Guide і Changelog, старонкі Search, Get Track, Add Item to Queue): у Development Mode `GET /search` — `limit` максімум **10** (было 50), па змаўчанні **5**; `GET /tracks/{id}` працуе, пакетны `GET /tracks?ids=` **выдалены**; у трэка выдалены `popularity`, `available_markets`, `linked_from` (`external_ids` вярнулі ў сакавіку); `market` у пошуку не патрэбны — пры токене карыстальніка бярэцца краіна акаўнта; `POST /me/player/queue?uri=…` не змяняўся (scope `user-modify-playback-state`, Premium, адказ 204; Spotify не абяцае парадак выканання каманд, якія ідуць адна за адной). Выдаліць або пераставіць трэк у чарзе Spotify па-ранейшаму нельга.
- Рашэнне:
  - **Пошук** (`src/providers/spotify/search.ts`): спасылка `open.spotify.com/(intl-xx/)track/ID` або `spotify:track:ID` → `GET /tracks/{id}`; іншая спасылка (альбом, плэйліст, `spotify.link`) — «не знайшоў»; інакш — `GET /search?type=track&limit=10` і выбар найлепшага: доля слоў запыту ў назве і выканаўцах + частка назвы ў запыце, мінус за караоке/remix/live/cover, калі глядач іх не пісаў; калі ні адно слова не супала (транслітарацыя) — першы вынік Spotify. Лакальныя, недаступныя ў краіне (`is_playable: false`, `restrictions` акрамя `explicit`) трэкі не бяруцца. Памылка Spotify (квота, сетка) — «Spotify не адказаў», а не «не знайшоў» (на Этапе 4 — у абодвух выпадках вяртанне баллаў).
  - **Правілы** (`core/rules.ts`) — як раней; паўтор правяраецца і па заказе, які грае зараз. Адмова — паведамленне ў доку.
  - **Адпраўка:** у Spotify трапляе толькі **першы** заказ і толькі за **15 с** да канца бягучай песні (`core/requests.ts`, `requestToSend`). Да запыту заказ адзначаецца `sentAt` і стан адразу запісваецца ў `localStorage` — новы лідар (ADR-015) не адправіць яго другі раз. Не атрымалася — адзнака здымаецца, паўтор праз 5 с.
  - **Паказ:** адпраўлены заказ застаецца ў нашай чарзе з нікам, а з «Далей у Spotify» хаваецца (адзін раз — тая ж песня можа быць і далей у плэйлісце). Калі Spotify пачынае граць адпраўлены заказ, ён становіцца бягучым з нікам і ключом заказу.
  - **«Наступная»** з заказамі ўключае першы заказ (як паказваюць док і оверлей). **«Прайграць зараз»** — `POST queue` (калі заказ яшчэ не там) + `POST next`; калі першы заказ ужо ў чарзе Spotify, а ўключаюць іншы — дзве «наступная» з паўзай 0,3 с (першы на імгненне пачынае граць і будзе адпраўлены нанова). Да 4 с док паказвае менавіта гэты заказ. Не атрымалася — заказы вяртаюцца як былі.
  - **«Выдаліць»** — з нашай чаргі. Калі заказ ужо ў чарзе Spotify (апошнія 15 с песні), бот запамінае яго (`skip`) і, калі ён пачне граць, адразу пераключае на наступную.
  - **Зверка з чаргой Spotify** (пры кожным чытанні `GET /me/player/queue`, `reconcileQueue`): адпраўлены заказ знік з чаргі і не грае (больш за 10 с пасля адпраўкі: Spotify перазапусцілі, чаргу ачысцілі, лідар знік да запыту) — адзнака здымаецца, заказ адправіцца нанова (лепш другі раз, чым згубіць заказ за баллы); неадпраўлены першы заказ стаіць **першым** у чарзе Spotify (Spotify аднавіў чаргу, або лідар адправіў, але не паспеў захаваць адзнаку) — лічыцца адпраўленым; выдалены адпраўлены заказ знік — забываем.
  - **Крайнія выпадкі:** стрымер сам пераключыў песню ў Spotify, калі заказ ужо ў чарзе, — заказ застаецца першым у чарзе Spotify і грае пасля новай песні; Spotify закрыты — заказы чакаюць у нашай чарзе (адпраўка толькі пры музыцы), а пасля адкрыцця зверка вырашае, ці адпраўляць нанова; змена лідара — гл. вышэй.
  - **«+ Тэставы заказ»** пры падключаным Spotify — сапраўдныя трэкі праз пошук (`SPOTIFY_TEST_QUERIES`, па чарзе: спасылкі, назвы па-беларуску і па-англійску, задоўгая «Rush — 2112» для правіла 12 хв), выдуманы нік гледача. Без Spotify — як раней.
  - **Квота:** пошук і адпраўка — толькі па падзеі (заказ, канец песні, кнопка), без дадатковых апытанняў; 429 — як у ADR-016 (пошук пры блакіроўцы не робіцца).
- Прычыны / альтэрнатывы: (а) адпраўляць заказ у Spotify адразу — тады «выдаліць» і «прайграць зараз» не працуюць (з чаргі Spotify нічога не прыбраць); (б) адпраўляць у самы апошні момант (1–2 с) — пры апытанні раз у 6–20 с бот можа не паспець, і Spotify уключыць плэйліст; 15 с — запас на недакладнасць лакальнага часу; (в) `PUT /me/player/play` з `uris` — замяніў бы кантэкст стрымера (плэйліст), чаго аўтар не хоча.
  - **Дапаўненне (2026-10-10, пасля праверкі аўтарам):** перамотка песні ў самы канец (у Spotify) не мяняе загаловак акна, і бот не паспяваў адправіць заказ — зайграў плэйліст. Цяпер: пакуль чакае неадпраўлены заказ, апытанне раз у 5 с; а калі Spotify усё ж сам перайшоў да **наступнай песні сваёй чаргі** (канец песні або «наступная» ў самім Spotify), бот адразу ўключае першы заказ (`missedRequest`): песня з плэйліста гучыць каля 1 с (з акном Spotify у OBS) або да 5 с (без яго). Калі стрымер сам выбраў іншую песню — не перабіваем, заказ зайграе пасля яе.
- Наступствы: перамотка песні ў самім Spotify не відаць да наступнага апытання — заказ можа трапіць у Spotify крыху раней або (рэдка) не паспець да канца песні, тады зайграе пасля наступнай. Калі стрымер прапусціць заказ хутчэй, чым бот апытае Spotify, зверка палічыць яго страчаным і адправіць нанова. Калі лідар знікне ў доле секунды паміж «у чаргу» і «наступная» пры «прайграць зараз», заказ зайграе пасля бягучай песні без ніка. Калі ў Spotify нічога не грае (плэйліст скончыўся), заказы не адпраўляюцца — BACKLOG B-016.

## ADR-018 · Twitch: уваход па кодзе (Device Code Flow), узнагарода і заказы за баллы, вяртанне баллаў, чат
- Дата: 2026-10-11 · Статус: прынята (Этап 4; праверана тэстамі і ў браўзеры з падробкай Twitch; аўтар праверыў з свайго акаўнта на канале — працуе, з іншых акаўнтаў — на наступным стрыме; паўза, ✕ і старыя замовы — пагоджана аўтарам)
- Кантэкст: дакументацыя Twitch на кастрычнік 2026 (Getting OAuth Access Tokens, Refreshing Access Tokens, Validating Tokens, Registering Your App, Handling WebSocket Events, EventSub Subscription Types, API Reference — Create / Update / Get Custom Reward, Get Custom Reward Redemption, Update Redemption Status, Send Chat Message; API guide — rate limits; Changelog 2025-06…2026-06 — для нашых метадаў змен няма):
  - **Device Code Flow:** `POST id.twitch.tv/oauth2/device` (`client_id`, `scopes`) → `device_code`, `user_code`, `verification_uri`, `interval`, `expires_in` (1800 с); апытанне `POST /oauth2/token` з `grant_type=urn:ietf:params:oauth:grant-type:device_code` — да пацверджання 400 `authorization_pending`. **Public-прыкладанне:** без Client Secret; access token — 4 гадзіны; refresh token **аднаразовы** і дзейнічае **30 дзён** (новы — пры кожным абнаўленні).
  - **Implicit grant:** токен у `#` адраса, без refresh token, патрабуе дакладны Redirect URI.
  - `GET /oauth2/validate` — абавязкова пры старце і кожную гадзіну; 401 — сесію спыніць.
  - **EventSub WebSocket:** `wss://eventsub.wss.twitch.tv/ws`, толькі user token; 10 с на падпіску пасля `session_welcome`; `keepalive_timeout_seconds` 10–600; `session_reconnect` — новае злучэнне з тымі ж падпіскамі; пры разрыве падпіскі адключаюцца (ствараць нанова), падзеі ў перапынку **не вяртаюцца**; да 3 злучэнняў на пару Client ID + карыстальнік.
  - `channel.channel_points_custom_reward_redemption.add` v1: scope `channel:read:redemptions` або `channel:manage:redemptions`, умова `broadcaster_user_id` (+ `reward_id`).
  - **Create Custom Reward:** `channel:manage:redemptions`, толькі Affiliate/Partner (інакш 403), назва ≤ 45 сімвалаў і ўнікальная ў канале, `prompt` ≤ 200, не больш за 50 узнагарод. **Update Custom Reward:** `is_paused` — гледачы бачаць, але не могуць купіць; `is_enabled: false` — узнагарода схаваная. Мяняць узнагароду і статусы заказаў можа **толькі Client ID, які яе стварыў** (403).
  - **Update Redemption Status:** толькі з `UNFULFILLED`; `CANCELED` вяртае баллы; 404 — заказ не знойдзены або ўжо не `UNFULFILLED`.
  - **Send Chat Message:** `user:write:chat`, `sender_id` = уладальнік токена, ≤ 500 сімвалаў, адказ `is_sent` / `drop_reason`.
  - **429:** колькі чакаць — у загалоўку `Ratelimit-Reset`.
  - **CORS (праверана 2026-10-11 са старонкі `http://127.0.0.1:5173`, падроблены Client ID):** `id.twitch.tv` (`/device`, `/token`, `/validate`) і `api.twitch.tv` (GET і PATCH з `Authorization`) адказваюць старонцы, цела адказу чытаецца. Загалоўкі `Ratelimit-*` браўзеру **не бачныя**. WebSocket CORS не мае.
- Рашэнне:
  - **Уваход — Device Code Flow, Twitch Application тыпу Public** (ADR-004). Док паказвае код і адкрывае `twitch.tv/activate` у сістэмным браўзеры (з дока OBS вокны адкрываюцца там, ADR-009), стрымер пацвярджае — док сам атрымлівае токены. Чаму не implicit grant: (1) адрас вяртання не патрэбны — працуе з любога хостынгу (Этап 5) без змены налад Twitch Application; (2) ёсць refresh token — уваход жыве, пакуль OBS з ботам адкрываюць хоць раз на 30 дзён, а implicit патрабуе ўваходу нанова пасля сканчэння токена; (3) у браўзеры, дзе стрымер ужо ўвайшоў у Twitch, не трэба ўводзіць пароль у доку.
  - **Scopes:** `channel:manage:redemptions` (уключае чытанне заказаў і EventSub) і `user:write:chat`. `channel:read:redemptions` з ADR-011 не патрэбны.
  - **Client ID** — пакуль поле ў доку (`settings.twitch.clientId`, не сакрэт); на Этапе 5 — убудаваць у зборку (BACKLOG B-018).
  - **Токены** — `localStorage` `spotify-bot:twitch:tokens:v1` з `userId` і `login` (з `/validate`). Абнаўляе **толькі лідар** (ADR-015) і адразу захоўвае новы refresh token; адначасова — адно абнаўленне. 401 → адзін refresh і паўтор; refresh не прыняты / 401 пасля яго / `revocation` → токены выдаляюцца, док паказвае «Уваход у Twitch састарэў». `/validate` — пры старце лідара і раз у гадзіну; без патрэбных scopes — просьба падключыцца нанова.
  - **Узнагарода** «Заказаць песню» (`src/sources/twitch/twitch.ts`): `prompt` з тлумачэннем, `cost` = цана з правілаў, `is_user_input_required`, `should_redemptions_skip_request_queue: false` (інакш нельга вярнуць баллы), колер Spotify. Яе id — у `spotify-bot:twitch:reward:v1`. Пры старце: па id → па назве сярод «сваіх» (`only_manageable_rewards`) → стварыць. Узнагарода з такой назвай, створаная не ботам, — паведамленне ў доку. Змена цаны ў наладах → `PATCH`. Раз у 10 хв і праз EventSub (`reward.update`, `reward.remove`) бот сочыць за ўзнагародай; выдалілі — створыць нанова.
  - **Заказы:** EventSub толькі ў лідары (адно злучэнне — адзін атрымальнік). Пасля кожнага новага злучэння — падпіскі, потым **даганялка**: `GET …/redemptions?status=UNFULFILLED&sort=OLDEST`. Заказ ідзе ў той жа пошук і правілы, што і тэставы (`processRequest` у `brain.ts`, ADR-017).
  - **Статусы і чат:** `FULFILLED` — калі песня **зайграла** (бягучая ≥ 3 с або ўжо прайграная), а не пры даданні ў чаргу: пакуль песня чакае, стрымер можа прыбраць яе ✕ — тады `CANCELED`, баллы вяртаюцца. Адмова (не знайшоў, правілы, «Spotify не адказаў», пусты заказ, Spotify не падключаны) — `CANCELED`. Паведамленні ў чат ад імя стрымера (тэксты `chat.*` у `be.ts`): «@нік «назва» дададзена, №N у чарзе» і «@нік <прычына>, баллы вернуты» — пра адмову толькі **пасля** таго, як Twitch прыняў `CANCELED`.
  - **Журнал заказаў** `spotify-bot:twitch:redemptions:v1` (`redemptions.ts`, чыстыя функцыі): этапы `processing → queued → fulfill / refund → done`, паведамленне ў чат, спробы і час паўтору. Сувязь песні з заказам — `QueueItem.redemptionId` у стане плэера (ADR-015). Запісы старэйшыя за 3 дні выдаляюцца.
  - **Крайнія выпадкі:**
    - паўторная дастаўка падзеі — `message_id` (апошнія 300) і id заказу ў журнале; падзея і даганялка не запускаюць адзін заказ двойчы;
    - змена лідара пасярэдзіне апрацоўкі — заказ застаецца `processing`, новы лідар апрацоўвае яго нанова, але спачатку правярае, ці песня ўжо ў чарзе; паведамленне ў чат, якое папярэдні лідар **пачаў** адпраўляць, не паўтараецца (лепш страціць адно, чым напісаць двойчы);
    - журнал сцёрты, а песня ў чарзе — не дублюецца; песня знікла з чаргі, не пачаўшы граць, — адзін паўтор, потым вяртанне баллаў;
    - EventSub: маўчанне даўжэй за keepalive (30 с) + 5 с — перападключэнне з паўзамі 1, 2, 5, 10, 30 с; `session_reconnect` — пераход без новай падпіскі; пасля звычайнага перападключэння — даганялка;
    - 429 — паўтор праз 30 с (`Ratelimit-Reset` недаступны); іншыя памылкі статусу — праз 5 с, 15 с, 1 хв, 5 хв; 404 на статус — стрымер ужо вырашыў сам у Twitch, паведамлення няма;
    - пакуль Spotify падключаецца — заказ чакае, а не адмяняецца.
  - **Пакуль бот не можа браць заказы — паўза (`is_paused`)**, а не схаваная ўзнагарода: Spotify не падключаны, абмежаваны або з памылкай (стан павінен пратрымацца ≥ 3 с, першыя 3 с пасля старту лідара паўзу не чапаем); старонка-лідар зачыняецца (запыт з `keepalive`, новы лідар здымае паўзу праз некалькі секунд); «Адключыць» Twitch. Калі OBS упаў і паўза не паспела — заказы, зробленыя больш за 10 хв таму, пры наступным запуску адмяняюцца з паведамленнем «бот не працаваў», свежыя трапляюць у чаргу.
- Прычыны / альтэрнатывы: (а) implicit grant — гл. вышэй; (б) Authorization Code з сакрэтам — патрэбны сервер (ADR-009); (в) `FULFILLED` адразу пры даданні ў чаргу — тады ✕ і страта чаргі не вярталі б баллы; (г) схаваць узнагароду замест паўзы — гледачы і стрымер думаюць, што яна знікла; (д) нічога не рабіць, калі бот не працуе — гледачы плацяць за заказы, якія ніхто не апрацуе; (е) чытаць заказы толькі апытаннем Helix — запазненне і лішнія запыты; EventSub + даганялка дае і хуткасць, і надзейнасць.
- **Дапаўненне (2026-10-11, пасля першай праверкі аўтарам):**
  - Адказы аўтара: паўза ўзнагароды, калі Spotify не падключаны, — так (бот ставіць і здымае паўзу сам за 3–5 с); ✕ вяртае баллы — так; старыя замовы пры запуску (>10 хв) — вяртанне баллаў, так; паўза па-за эфірам — не патрэбна (BACKLOG B-019 адхілена).
  - Тэрміны інтэрфейсу і чата (аўтар): «замова» замест «заказ» (`Замовы гледачоў`, `+ Тэставая замова`, `Правілы замоў`), «Кошт» замест «Цана», «Чарга» замест «Далей у Spotify», «оверлэй» замест «оверлей»; блок бягучай песні — без загалоўка «Зараз грае» і без «?».
  - Узнагарода называецца **«Замовіць песню»**. Бот сам перайменоўвае сваю ўзнагароду, калі назва адрозніваецца (ён ведае яе id), і знаходзіць яе па старой назве «Заказаць песню», калі id страчаны (`LEGACY_TITLES`).
  - Паведамленне пра прынятую замову — **«Гурт — Назва стала ў чаргу»** (без ніка і нумара, як папрасіў аўтар). Правапіс: пасля галоснай «у» → «ў» («стала ў чаргу»), паміж выканаўцам і назвай — працяжнік з прабеламі; «стала» — у жаночым родзе, бо маецца на ўвазе «песня». Паведамленні пра адмову застаюцца з `@нік` — гледачу трэба ведаць, што баллы вернуты менавіта яму.
- Наступствы: калі OBS з ботам не адкрываўся 30 дзён — уваход у Twitch нанова. Калі стрымер рэдагуе або выдаляе ўзнагароду ў Twitch, бот вяртае яе да сваіх налад або стварае нанова (каб спыніць — «Адключыць» Twitch). Тэксты ў чат — па-беларуску, нік гледача — `user_name` з Twitch.

## ADR-019 · Хостынг: GitHub Pages, галіна `gh-pages` публічнага рэпазіторыя
- Дата: 2026-10-11 · Статус: прынята (выбар аўтара); у OBS — чакае праверкі
- Кантэкст: аўтар нагадаў дамоўленасць (ADR-009): для працы бота дастаткова запусціць OBS. Пакуль старонкі аддае dev-сервер (`npm run dev`), гэта не так. Рэпазіторый з кодам прыватны, а GitHub Pages для прыватных рэпазіторыяў платны. Праверка 2026-10-11: obs-websocket у аўтара працуе (адказ `Hello` са старонкі `http://127.0.0.1:5173`); са старонкі `https://example.com` ва ўбудаваным браўзеры Claude (Chromium 152) злучэнне з `ws://127.0.0.1:4455` **заблакавана** — ахова лакальнай сеткі (Local Network Access) у новых Chromium. У OBS 32 убудаваны старэйшы Chromium (CEF 127 [па памяці, не праверана]), дзе гэтай аховы няма — трэба праверыць у OBS (BACKLOG B-004).
- Рашэнне: зборка (`dist/`) публікуецца камандай `npm run deploy` (`scripts/deploy.mjs`) у галіну `gh-pages` рэпазіторыя `mashninski/spotify-bot`; GitHub Pages аддае яе па https (`https://mashninski.github.io/spotify-bot/`). **Удакладненне (2026-10-11):** спачатку планаваўся асобны публічны рэпазіторый толькі са зборкай; аўтар вырашыў зрабіць публічным сам `spotify-bot` — ён хоча, каб іншыя стрымеры маглі ўзяць прыкладанне. Перад гэтым Claude праверыў усю гісторыю (44 commits, усе галіны): `.env` у git не трапляў, у `.env.example` — толькі адрас і порт OBS, токенаў, ключоў і пароляў няма, Client ID — толькі падробленыя тэставыя, пошта ў commits — `noreply` GitHub. Кожная публікацыя — асобны commit з хэшам зыходнага commit, без `push --force`. Публікуе Claude пасля праверкі змен (ADR-005; рэпазіторый і ўключэнне Pages — аднойчы аўтар).
- Прычыны / альтэрнатывы: (а) Cloudflare Pages з прыватнага рэпазіторыя — больш крокаў для аўтара (акаўнт, доступ да GitHub); (б) лакальныя файлы (`file://`) — Spotify не прымае такі адрас вяртання, уваход немагчымы; (в) зрабіць `spotify-bot` публічным — аўтар хоча прыватны код; (г) GitHub Pro — грошы.
- Наступствы: старонкі ў OBS — з інтэрнэту (без інтэрнэту стрым усё роўна немагчымы). Новы адрас — новы `localStorage`: Spotify, Twitch, пароль OBS і правілы ўводзяцца нанова адзін раз (B-023), узнагароду бот знойдзе сам. У Spotify Dashboard дадаецца новы Redirect URI. Калі ў OBS https-старонка не дасягне `ws://127.0.0.1:4455`, не будзе хвалі і хуткага выяўлення змен у Spotify — тады шукаем іншы спосаб (напрыклад, оверлэй як лакальны файл толькі для ўзроўню гуку).

## ADR-020 · Замовы відэа з YouTube: асобная ўзнагарода, агульная чарга, плэер у оверлэі
- Дата: 2026-10-17 · Статус: прынята (сэнс прадукту — аўтар; тэхнічная рэалізацыя — Claude; галіна `feature/youtube`, чакае праверкі аўтарам у OBS)
- Кантэкст (рашэнне аўтара 2026-10-17): другая ўзнагарода Twitch — відэа з YouTube (кошт па змаўчанні 1000, мяняецца ў доку; ствараецца і ставіцца на паўзу, як «Замовіць песню»). Глядач дасылае толькі спасылку, відэа да 12 хв. Чарга агульная са Spotify, парадак — па часе замовы; правілы тыя ж: ліміт 2 замовы ад гледача — **агульны** на песні і відэа, дублі забаронены, адмова вяртае балы, паведамленні ў чат па-беларуску. Фільтраў зместу няма, але відэа, якое нельга ўбудаваць (забарона ўбудавання, узроставае абмежаванне, трансляцыя, выдалена, задоўгае), — адмова з вяртаннем балаў. Оверлэй: 5 наступных замест 3 з значкамі крыніцы; падчас відэа — чырвоны стыль, лагатыпы мяняюцца месцамі, над палоскай — плашка з відэа.
- Праверана 2026-10-17 ва ўбудаваным браўзеры (Chromium 152) з сапраўдным YouTube:
  - **oEmbed** `https://www.youtube.com/oembed?format=json&url=…` адказвае старонцы (CORS ёсць), без ключа: `title`, `author_name` (канал); неіснуючае відэа — 400. Даўжыні ў oEmbed няма.
  - **YouTube IFrame Player API**: калі `videoId` перададзены пры стварэнні плэера, ужо ў `onReady` (≈0,3–0,5 с, відэа не грае — стан CUED) ёсць `getDuration()` і `getVideoData()` (`title`, `isPlayable`, `isLive`). Невядомае або забароненае відэа — `onError` 150 (код 100/101 YouTube на практыцы не дае — адрозніваем па oEmbed).
  - **Са старонкі на IP-адрасе (`http://127.0.0.1:…`) YouTube не дае ўбудаваць ніводнае відэа** («Видео недоступно», `errorCode: auth`), з `http://localhost:…` і з https (`example.com`) — працуе. GitHub Pages (ADR-019) — https, падыходзіць; для распрацоўкі — `http://localhost`.
- Рашэнне:
  - **Тып даных.** Відэа — той жа `Track` з `source: 'youtube'`, `videoId`, `id = yt:<videoId>`, `artist` = канал, `uri` няма. Таму агульныя чарга, правілы (дублі, ліміт ад гледача), журнал замоў Twitch, «выканана» праз 3 с прайгравання, ✕ з вяртаннем балаў працуюць без змен. Правілы: `videoPrice` (1000) і `videoMaxDurationMin` (12) — асобна ад песень; explicit для відэа не правяраецца.
  - **Twitch.** Узнагарода «Замовіць відэа з YouTube» (колер `#FF0000`), id — `spotify-bot:twitch:reward:video:v1`. Код адной узнагароды (ADR-018) абагульнены на дзве (`song`, `video`): пошук па id / назве, стварэнне, кошт, паўза, праверка раз у 10 хв, даганялка — для кожнай. Падпіскі EventSub — без `reward_id` (умова толькі `broadcaster_user_id`): тры падпіскі на ўсе ўзнагароды канала, падзеі чужых узнагарод адкідаюцца. У запіс журнала дададзены `kind`. Спасылка YouTube ва ўзнагародзе песні і не-YouTube ва ўзнагародзе відэа — адмова з падказкай у чаце.
  - **Праверка відэа** (`src/youtube/`): спасылкі `youtube.com/watch?v=`, `youtu.be/`, `/shorts/`, `/embed/`, `/live/`, `m.`, `music.`, `youtube-nocookie.com` → 11 сімвалаў id. Потым oEmbed (назва, канал; 400/404 — «не знайшлося», 401/403 — «нельга ўбудаваць», памылка сеткі — «YouTube не адказаў») і схаваны плэер у старонцы-лідары (без гуку, не грае): `isLive` або даўжыня 0 — трансляцыя; `onError` або `isPlayable: false` — нельга ўбудаваць (сюды трапляюць і ўзроставыя абмежаванні); 15 с без адказу — «YouTube не адказаў». Ключоў і платных сэрвісаў няма.
  - **Дзе грае відэа — толькі ў оверлэі.** Мозг (ADR-015) можа быць у доку, але відэа ў доку не грае ніколі. Сярод старонак-оверлэяў адна бярэ Web Lock `spotify-bot:video` — «уладальнік плэера»: грае з гукам і раз у секунду (і пры змене стану) паведамляе лідару праз шыну (`video-report`: ключ, стан, пазіцыя). Іншыя оверлэі (калі стрымер зрабіў некалькі крыніц) паказваюць тое ж відэа без гуку і падцягваюць пазіцыю. Пазіцыя і паўза — у стане плэера лідара, таму перазагрузка оверлэя ўключае відэа з таго ж месца, а змена лідара відэа не чапае (плэер жыве ў оверлэі). Дубля няма: гук дае толькі ўладальнік замка.
  - **Пераходы Spotify ↔ відэа.** Стан `PlayerState.video` (ключ відэа, як працягнуць Spotify, час старту і апошняга паведамлення, лічыльнік перамоткі) захоўваецца разам з чаргой (ADR-015).
    - Першае ў чарзе — відэа, а песня ў Spotify скончыцца праз ≤ 1,2 с (лакальны час, пакуль чакае замова — апытанне раз у 5 с) — паўза Spotify, відэа становіцца бягучым; пасля відэа — «наступная» ў Spotify. Калі Spotify усё ж паспеў перайсці да наступнай песні (перамотка, затрымка), — паўза адразу, а пасля відэа гэтая песня ідзе з пачатку (`seek 0` + `play`).
    - «Уключыць зараз» / «Наступная» на відэа — паўза Spotify адразу, пасля відэа — наступная песня (як і для замоў песень, бягучая песня не вяртаецца).
    - Пасля відэа: наступнае відэа — адразу (Spotify застаецца на паўзе); замова песні — у чаргу Spotify + «наступная» + `play`; інакш — «наступная» (або працяг) + `play`. Чакаем пацверджання Spotify, як для кнопак (ADR-016).
    - Падчас відэа адказы Spotify не мяняюць бягучую песню. Калі стрымер сам уключыў музыку ў Spotify (паўза ўжо была пацверджана, а Spotify зноў грае) — відэа спыняецца, як пры «Наступная»: перамагае дзеянне стрымера, гук не накладваецца.
    - Кнопкі дока падчас відэа: паўза / працяг — відэа; «Наступная» — канец відэа; «Папярэдняя» — відэа з пачатку; гучнасць — гучнасць відэа (налада). ✕ і ▶ на радках чаргі — як для песень.
    - **Вартаўнік:** калі ад плэера няма паведамленняў 12 с (оверлэй не адкрыты, выдалены, плэер упаў), плэер жывы, але відэа не пачалося за 90 с (запас на рэкламу перад відэа), або плэер паведаміў пра памылку — відэа заканчваецца, музыка працягваецца; калі відэа яшчэ не пачало паказвацца — балы вяртаюцца («відэа не атрымалася паказаць»). «Выканана» ў Twitch — толькі калі плэер сапраўды паказвае відэа 3 с (не калі відэа проста стала бягучым).
    - Пераход «відэа → наступнае» — адным змяненнем стану: оверлэй не бачыць паміж імі «нічога не грае» (палоска не міргае).
  - **Хваля падчас відэа.** Гук відэа з iframe YouTube у самой старонцы прааналізаваць нельга (іншы origin, Web Audio не мае доступу). Таму — obs-websocket `InputVolumeMeters` той крыніцы Browser Source, у якой адкрыты оверлэй: бот сам знаходзіць яе (`GetInputList` → `browser_source` з `overlay.html` у адрасе і «Управлять звуком через OBS»), або стрымер выбірае крыніцу ў доку. Без яе — «імітацыя рытму», пакуль відэа грае.
  - **Гучнасць відэа** — налада дока (0–100, па змаўчанні 40: YouTube і Spotify нармалізуюць гучнасць прыкладна аднолькава, таму 40 ціхэй за звычайную гучнасць Spotify). Падчас відэа паўзунок гучнасці ў доку кіруе відэа.
  - **Плэер у оверлэі:** без кнопак YouTube (`controls=0`), без поўнага экрана, субтытры, уключаныя аўтарам відэа, выключаюцца (`unloadModule('captions')`, не ў дакументацыі — B-031). Калі браўзер не дае ўключыць відэа з гукам 4 с — уключаецца без гуку (каб хоць было відаць). **Плашка з’яўляецца, калі само відэа прайгралася 4 с** (па часе відэа, а не па падзеях плэера — загрузка і буферызацыя не лічацца; заўвага аўтара 2026-10-17): першыя секунды YouTube паказвае над відэа назву, кнопку паўзы і «Другие видео», без мышы яны знікаюць праз 2–3 с; гук відэа ідзе адразу. Калі відэа за 8 с пасля загрузкі так і не пайшло (рэклама, памылка), плашка з’яўляецца ўсё роўна — каб не хаваць рэкламу і памылкі YouTube (правілы YouTube для ўбудаванага плэера забараняюць закрываць плэер і хаваць рэкламу). Нічога паверх плэера не малюецца.
  - **Рэклама:** прэ-ролы YouTube ва ўбудаваным плэеры будуць трапляцца на манетызаваных відэа (у тым ліку відэа лэйблаў). Бот не можа іх выключыць або прапусціць: у IFrame API такой магчымасці няма, а хаваць або закрываць рэкламу забараняюць правілы YouTube. Рэклама гучыць у эфіры і бачная ў плашцы; відэа замовы пачынаецца пасля яе. Іншыя оверлэі (не ўладальнікі) — без гуку, пазіцыя падцягваецца, калі разыходзіцца больш чым на 3 с.
  - **Праверка ў OBS да зліцця:** `npm run deploy:next` публікуе зборку ў папку `next/` на GitHub Pages (`…/spotify-bot/next/`), асноўны адрас не мяняецца. Сайт той жа — `localStorage` агульны, Spotify і Twitch падключаць нанова не трэба; док і оверлэй павінны быць адной версіі. Асноўная публікацыя (`npm run deploy`) замяняе ўвесь сайт, разам з `next/`.
  - **Оверлэй:** памер Browser Source **520×500** (было 520×170): зверху месца пад плашку відэа (16:9), пад ёй — палоска, ніжэй — 5 наступных. Палоска стаіць на адным месцы, з’яўляецца відэа ці не. Падчас відэа — колер `--accent` чырвоны (`#ff3b3b`), лагатыпы мяняюцца месцамі, назва відэа і канал з нікам. `overlay.html?demo=video` — тэставы выгляд з відэа (каб размясціць крыніцу ў сцэне).
- Прычыны / альтэрнатывы: (а) YouTube Data API — патрэбны ключ (сакрэт) і квота; oEmbed + плэер даюць усё без ключа; (б) іграць відэа ў лідары — калі лідар док, відэа не ўбачаць гледачы; (в) лідарам заўсёды рабіць оверлэй — ламае ADR-015 (бот не працуе з закрытым оверлэем) і не вырашае некалькі оверлэяў; (г) аналіз гуку ў старонцы — немагчымы для iframe з іншага origin; (д) спыняць Spotify «наступнай» замест паўзы — тады песня з плэйліста гучыць да пачатку відэа.
- Наступствы / рызыкі: у плэеры YouTube можа быць рэклама (час відэа ідзе пасля яе); бот не можа яе выключыць. DMCA: Twitch можа выдаліць запіс або даць папярэджанне за музыку і чужое відэа ў эфіры — бот гэта не правярае (фільтраў зместу няма па рашэнні аўтара). Калі оверлэй не ў бягучай сцэне, гук відэа ў эфір не трапляе (OBS змешвае толькі актыўныя крыніцы). Калі ў OBS некалькі асобных крыніц з оверлэем, гук дае толькі адна (лепш адна крыніца, дададзеная ў іншыя сцэны як «існуючая»).
- **Дапаўненне 2 (2026-10-17, рэклама, пытанне аўтара «на 100% пазбавіцца ад рэкламы»):**
