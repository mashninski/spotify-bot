## ADR-001 · Мовы працы
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: аўтар размаўляе з Claude па-руску, але праект вядзецца па-беларуску.
- Рашэнне: размова з аўтарам — руская; каментарыі ў кодзе, дакументацыя, commit-паведамленні, GitHub (PR, issues, README), тэксты прыкладання — беларускія. Тэхнічныя тэрміны, імёны зменных, функцый і файлаў — англійскія. Выключэнне: `CLAUDE.md` і `docs/CLAUDE_PROJECT_INSTRUCTIONS.md` напісаны па-руску, бо гэта правілы зносін з аўтарам, а не дакументацыя праекта (удакладнена аўтарам 2026-10-10).
- Наступствы: тэксты для гледачоў стрыма вызначаюцца асобна (гл. `PROJECT.md`, адкрытае пытанне 4).

## ADR-002 · Кампактная сістэма дакументацыі
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: патрэбны захаванне кантэксту паміж чатамі без ручнога абслугоўвання аўтарам.
- Рашэнне: чатыры працоўныя дакументы (`PROJECT`, `LOG`, `DECISIONS`, `BACKLOG`) + `CLAUDE.md` + інструкцыя для Claude Project + згенераваны `CONTEXT.md`. Журнал змен, выдаленняў і перапрацовак — у адным `LOG.md` (розныя тыпы запісаў). Новыя файлы дадаем толькі праз рашэнне ў гэтым журнале.
- Прычыны: менш файлаў — прасцей шукаць і падтрымліваць. Альтэрнатыва (асобныя журналы па тыпах) адкінутая як залішне складаная.

## ADR-003 · Адна буйная задача — адна сесія
- Дата: 2026-10-10 · Статус: прынята
- Рашэнне: буйная задача або самастойны этап вядзецца ў асобным чаце Claude ці сесіі Claude Code. Кантэкст новай сесіі бярэцца з дакументаў у `docs/`. Паміж Claude Code і звычайным чатом Claude аўтаматычнай сінхранізацыі няма; для чата без доступу да файлаў выкарыстоўваецца `docs/CONTEXT.md`, загружаны ў веды Claude Project.
- Прычыны: эканомія токенаў, якасць, выразная мяжа этапаў.

## ADR-004 · Twitch Application: існуючае ці новае
- Дата: 2026-10-10 · Статус: **прапанавана** (чакае рашэння аўтара)
- Кантэкст: у аўтара ёсць акаўнт Twitch Developer і Application ад іншага праекта.
- Прапанова: **акаўнт выкарыстоўваем той самы**; для гэтага праекта **ствараем новае Application**.
- Прычыны [вывад, не праверана на практыцы]: у кожнага праекта свой Client Secret, свае Redirect URL і ўласныя scopes; пры перавыпуску сакрэту ў адным праекце не ламаецца другі. Выкарыстанне старога Application тэхнічна магчыма (дадаць Redirect URL), але звязвае праекты.
- Наступствы: рэгістрацыя Application патрэбна толькі на Этапе 3 (аўтарызацыя Twitch). Да гэтага часу нічога ў Twitch Developer рабіць не трэба.
