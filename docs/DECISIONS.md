## ADR-004 · Twitch Application: існуючае ці новае
- Дата: 2026-10-10 · Статус: **прапанавана** (чакае рашэння аўтара)
- Кантэкст: у аўтара ёсць акаўнт Twitch Developer і Application ад іншага праекта.
- Прапанова: **акаўнт выкарыстоўваем той самы**; для гэтага праекта **ствараем новае Application**.
- Прычыны [вывад, не праверана на практыцы]: у кожнага праекта свой Client Secret, свае Redirect URL і ўласныя scopes; пры перавыпуску сакрэту ў адным праекце не ламаецца другі. Выкарыстанне старога Application тэхнічна магчыма (дадаць Redirect URL), але звязвае праекты.
- Наступствы: рэгістрацыя Application патрэбна толькі на Этапе 3 (аўтарызацыя Twitch). Да гэтага часу нічога ў Twitch Developer рабіць не трэба.

## ADR-005 · Самастойнасць Claude у распрацоўцы і ініцыятыва пераходаў
- Дата: 2026-10-10 · Статус: прынята
- Кантэкст: аўтар — пачатковец і не хоча ўзгадняць кожны тэхнічны крок; акрамя таго, доўгія чаты дорага каштуюць у токенах.
- Рашэнне: (1) у распрацоўцы Claude дзейнічае сам і працуе столькі, колькі трэба: выбірае рашэнні, піша код, ставіць залежнасці, правярае, робіць commit, push і зліццё сваіх галін у `main`. Пытаць аўтара абавязкова толькі пра грошы, сакрэты, дзеянні ад яго імя ў знешніх акаўнтах, незваротныя дзеянні з гісторыяй/данымі і сэнс прадукту (што ўмее бот). (2) Claude сам сочыць за памерам чата і, калі ён разросся, сам прапануе пераход з гатовым промптам — мэта эканомія токенаў.
- Прычыны / альтэрнатывы: альтэрнатыва «пытаць пра кожны крок» запавольвае працу і перакладае на пачаткоўца тэхнічныя рашэнні.
- Наступствы: абноўлены `CLAUDE.md` (раздзелы 0, 5, 8) і `docs/CLAUDE_PROJECT_INSTRUCTIONS.md`. Інструкцыю ў Claude Project аўтару трэба замяніць уручную (гл. `SETUP.md`).

## ADR-006 · Архітэктура: лакальнае прыкладанне + вэб-старонкі для OBS, TypeScript
- Дата: 2026-10-10 · Статус: **прапанавана** (канчаткова — пасля адказу аўтара пра платформу)
- Кантэкст: патрэбны оверлей, які стрымер рухае ў кожнай сцэне, док-панэль з кіраваннем і просты ўсталёўка на чужы кампутар.
- Рашэнне: невялікае лакальнае прыкладанне (фонавы працэс на кампутары стрымера) з убудаваным вэб-серверам на `localhost`. Яно аддае дзве старонкі: оверлей (дадаецца ў OBS як *Browser Source* — звычайная крыніца, якую можна рухаць і маштабаваць у кожнай сцэне) і док (OBS → *Docks → Custom Browser Docks*). Мова — **TypeScript** і на серверы (Node.js), і ў старонках. Унутры — модулі: `music provider` (Spotify; пазней YouTube), `request source` (баллы канала Twitch; пазней чат-каманды), агульная чарга і стан, вэб-інтэрфейс. Распаўсюд — адзін выканальны файл (спосаб зборкі выбераем на Этапе 5).
- Прычыны / альтэрнатывы: (а) родны плагін OBS на C++ — складана, зборка пад кожную версію OBS і АС, рызыка падзення OBS; (б) скрыпт OBS на Python/Lua — патрабуе ўсталяванага Python, слабыя магчымасці; (в) толькі Browser Source без сервера — оверлей і док не могуць надзейна дзяліць стан і бяспечна захоўваць tokens. Лакальны сервер — стандартны падыход для такіх прылад. TypeScript — адна мова на ўсё, шмат бібліятэк для Spotify/Twitch.
- Наступствы: налады і tokens карыстальніка захоўваюцца ў файле налад прыкладання ў профілі карыстальніка, а не ў `.env` (`.env` — толькі для распрацоўкі). OBS WebSocket для MVP не патрэбны.

## ADR-007 · Уласная чарга заказаў, Spotify атрымлівае песні па адной
- Дата: 2026-10-10 · Статус: **прапанавана**
- Кантэкст: Spotify Web API умее толькі **дадаваць** трэк у чаргу і **чытаць** чаргу; выдаліць трэк з чаргі або змяніць парадак нельга (публічнага endpoint няма, гл. форум Spotify for Developers). Аўтару патрэбны «выдаліць» і «прайграць зараз» без змены астатняй чаргі.
- Рашэнне: прыкладанне трымае сваю чаргу заказаў. У Spotify перадаецца толькі наступная песня, незадоўга да канца бягучай (або адразу — пры «прайграць зараз»: дадаць у чаргу Spotify + «наступная»). Выдаленне — проста з нашай чаргі (у Spotify яна яшчэ не трапіла). Калі заказаў няма, паказваем наступныя трэкі з кантэксту Spotify (`GET /me/player/queue`). Стан Spotify чытаем апытаннем кожныя ~1–3 с (push-падзей у Web API няма).
- Прычыны / альтэрнатывы: (а) класці ўсе заказы адразу ў чаргу Spotify — нельга выдаліць і пераставіць; (б) асобны плэйліст-«чарга» — прыбірае кантэкст стрымера і патрабуе лішніх правоў.
- Наступствы: кіраваць трэкамі з кантэксту Spotify (не заказамі) будзе абмежавана — дакладна высветлім пры рэалізацыі. Ліміты запытаў Spotify у Development Mode трэба праверыць на практыцы.

## ADR-008 · Падключэнне Spotify і Twitch для любога стрымера
- Дата: 2026-10-10 · Статус: **прапанавана**
- Кантэкст: з лютага 2026 Spotify Development Mode: да 5 карыстальнікаў на Client ID, уладальнік прыкладання павінен мець Premium; Extended Quota — толькі для арганізацый з 250k+ MAU (крыніцы: Spotify February 2026 Migration Guide, Web API Changelog July 2026). Кіраванне прайграваннем праз API патрабуе Premium. Twitch: абнавіць статус узнагароды (выканана / вярнуць баллы) можа толькі тое прыкладанне (Client ID), якое стварыла ўзнагароду (Twitch API Reference, Update Redemption Status).
- Рашэнне: **Spotify** — кожны стрымер стварае свой бясплатны Spotify Developer App (крокавая інструкцыя ў наладах прыкладання), устаўляе свой Client ID; аўтарызацыя праз Authorization Code + PKCE (без Client Secret). **Twitch** — адно наша Application тыпу *Public*, аўтарызацыя праз Device Code Flow (стрымер націскае «Падключыць» і ўводзіць код на twitch.tv); прыкладанне само стварае ўзнагароду «Заказаць песню», каб умець вяртаць баллы пры памылцы.
- Прычыны / альтэрнатывы: адзін агульны Spotify Client ID на ўсіх — максімум 5 стрымераў, гэта не працуе для распаўсюду. Існуючую ўзнагароду аўтара, створаную ў панэлі Twitch, можна чытаць, але нельга аўтаматычна вярнуць па ёй баллы.
- Наступствы: патрабаванне для карыстальнікаў — Spotify Premium. Па звестках трэцяга боку (не пацверджана Spotify), з чэрвеня 2026 аўтарызацыя Spotify можа дзейнічаць 6 месяцаў — прыкладанне павінна ўмець папрасіць падключыцца нанова.
